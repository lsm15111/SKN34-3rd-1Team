# 구현 현황

[메인 README](../README.md) · [문서 목록](README.md) · [아키텍처 README](architecture/README.md)

기준일: 2026-09-08. 현재 저장소의 production 코드·설정·테스트에 있는 기능을 정리합니다.
아래의 **구현됨**은 코드와 검증 경로가 있다는 뜻이며, 운영 배포 완료나 실데이터 정확도 입증을 뜻하지 않습니다.

현재 검색 정책은 [v5 개선 기록](search-relevance-v5-fix.md)을 우선 참고하세요. 시스템 날짜·서울 표제를
후보 검색어에서 제외하고, 관련도와 자격 미확인을 분리했습니다. 화면은 서버 관련도순을 보존하고
작은 `새 검색` 버튼과 적용 조건 요약을 제공합니다. 아래 C01/C02/v4 및 과거 테스트 수치는 당시 기록입니다.
v5의 코드 회귀 통과를 실제 모델 검색 정확도 향상으로 해석하지 않습니다.
후속 실제 비교에서는 지원금·컨설팅·영화 후반작업을 구분하는 지침과 랭킹 전용 Sol/low 설정을
채택했습니다. Luna의 지침 추가·추론 변경만으로 남았던 오추천과 빈 결과도 삭제하지 않고
[고정 후보 진단 기록](../evaluation/support-program-search/runs/search-precision-v5-20260907-v1/README.md)에 보존합니다.
이는 20개 후보의 소규모 AI 초안 대조이며 전체 검색 정확도 합격이나 후보 Recall 개선을 뜻하지 않습니다.

기획서 전체와의 차이 및 다음 개발의 우선순위·선행 조건·완료 기준은
[기획 정합성·개발 전략](development-strategy-20260907.md)에 정리했습니다.
이번 추가 버그 수정·실행 검증은 [추가 검수 기록](project-review-20260907.md)을 참고하세요.
이전 버그 수정 검수에서는 사용자 소켓 연결 승인 후 JDK 21·실제 MySQL 8.4에서 Core 전체 **379개 테스트(실패·오류·건너뜀 0)**도
완료했습니다. 이전에 검증하지 못했던 DB 통합 43개를 포함하며, 실제 모델 품질·운영 준비 완료와는 구분합니다.

후속 C01은 **익명 기업 조건 입력·적용과 실제 검색 반영**으로 범위를 좁혀 구현했습니다. 당시 수동 폼으로
지역·업종·설립일·지원 목적을 명시적으로 적용하고, 검색마다 당시 조건을 표시했습니다.
[C01 구현·검증 기록](company-conditions-search.md)은 최초 구현 당시 기록입니다.
당시 C01 검증은 Frontend **208개**, AI Service **256개**, JDK 21·실제 MySQL 8.4 Core **421개** 테스트가
통과했습니다. 브라우저에서는 별도 가상 응답으로 입력·변경·해제·초기화와 실제 POST 전송을 확인했습니다.
후속 [원문 우선 자격 검토](source-first-eligibility-review.md)는 대상·지역별 공식 API 본문 인용과
확인 필요 공고 분리를 추가했습니다. 이번 검증은 Frontend **236개**, AI Service **319개**, JDK 21·실제 MySQL 8.4
Core **433개**가 통과했고, 사용자 승인 후 로컬 Core·AI를 재빌드·재시작했습니다. 실제 모델 의미 정확도 검증은 별도입니다.
후속 [C02 조건 변경 대화](conversation-condition-update.md)는 현재 검색 의도·기업 조건에서 변경안만 해석하고,
사용자가 확인한 뒤 검색하는 흐름을 추가했습니다. 정보가 모호하면 질문하고, 확인하지 않은 초안은 적용하지 않습니다.
당시 C02 전체 검증은 Frontend **287개**, AI **459개**, JDK 21·실제 MySQL 8.4 Core **508개**가 통과했고
로컬 Core·AI를 재빌드·재시작했습니다. 실제 해석 3건 모두 HTTP·계약 검증을 통과했으나,
1건에서 기존 사업화 목적의 축약을 관찰했습니다. 일반 의미 정확도나 Q01 품질 게이트 합격으로 취급하지 않습니다.
기업 단계 구분, 첨부까지 포함한 전체 신청 요건 대조(E01 전체), 영구 프로필 저장은 아직 구현하지 않았습니다.

후속 UI 간소화에서는 기업 조건 수동 입력 패널·조건 적용/전체 초기화 버튼·조건 칩의 개별 해제·
접수 상태 선택 상자와 상시 장문 안내를 제거했습니다. 현재는 조건 변경·해제나 전체 접수 상태 요청을
대화로 전달하고, 변경 제안을 확인한 뒤 검색합니다. 기본 접수 중 검색, 새 대화·새로고침 초기화,
검색 당시 조건 스냅샷과 백엔드 자격 검증은 유지합니다. 이 변경의 현재 흐름은
[Frontend 안내](../frontend/README.md#화면과-현재-동작)와 [대화 조건 계약](conversation-condition-update.md)에 정리했습니다.
UI 간소화 후 Frontend 전체 **29파일 281개**(15.52초), 타입 검사·lint·production build가 통과했습니다.
삭제된 수동 폼 전용 테스트를 정리하고 대화 기반 변경·해제·스냅샷 회귀를 보강한 결과입니다.
실행 중인 Web의 `/`·`/chat`에서도 패널 제거를 확인했습니다. 백엔드 변경·재시작이나 추가 유료 호출은 없었습니다.
이어 정상 공고 상태 패널과 공고 수·인덱스·동기화 시각·제공처별 목록도 화면에서 제거했습니다.
내부 준비 상태 확인과 검색 차단·재시도는 유지하고 준비 중·장애·부분 검색만 짧게 안내합니다.
최신 Frontend 전체 **29파일 289개**(12.79초), 타입 검사·lint·production build가 통과했고
로컬 브라우저에 반영된 정상 화면에서도 패널 부재를 확인했습니다. 추가 유료 호출은 없었습니다.
조건 확인 카드도 검색 의도·변경할 조건·검색/취소 버튼 중심으로 축약했습니다. 전후 비교표와 미입력
항목·긴 안내는 제거하고, 해제와 기존 조건 유지는 간단히 구분합니다. 추가 확인은 질문과 답변 안내만
표시하며 자동 검색으로 바꾸지는 않았습니다. 최신 Frontend 전체 **29파일 293개**(11.26초)와
타입 검사·lint·production build가 통과했습니다. 유료 호출 없이 로컬 화면 모듈 반영을 확인했습니다.

후속 [검색 랭킹 시간 초과·인용 오류 수정](support-program-ranking-timeout-fix.md)은 랭킹 전용 시간 예산과
명시적 504 안내, 원문 번호 선택·인용 복원을 추가했습니다. AI 전체 **564개**, Frontend 전체 **301개**,
JDK 21·실제 MySQL 8.4 Core 전체 **512개**, 검색 평가 도구 오프라인 **67개**가 통과했습니다.
로컬 Core·AI 반영 후 동일 서울 검색 2회는 **200 / 27.494초·23.624초 / 5건·4건**으로 응답했고
화면 응답 계약·원문 인용 검사를 통과했습니다. 당시 서울 정보만으로 서초구 자격을 MATCH로 판단하는
의미 오류를 관찰하여, 검색 오류 수정과 지역 자격 정확도·전체 추천 품질을 구분했습니다.
후속 [지역 자격 범위·근거 개선](region-eligibility-scope-fix.md)은 상·하위 지역 포함 방향, 실제 지역
구절 인용, 이전 허용 대안을 보강했습니다. 최신 AI 전체 **572개**가 통과했고 합성 실제 검증은
초기 **22/24** 이후 예외 보완 및 서울·부산 재검증 **16/16**을 확인했습니다. 유료 API 총 5회이며
실제 카탈로그 검색 재검증이나 일반 정확도 입증은 아닙니다. 사용자 승인 후 2026-09-07 AI만 로컬
재빌드·재시작했고, 배포 소스 5개 해시 일치와 상태·검색 준비 API의 HTTP 200을 확인했습니다.
Core·Web·MySQL·Qdrant 및 데이터 볼륨은 유지했으며, 반영 확인 중 추가 유료 호출은 하지 않았습니다.

현재 **3단계는 제한적인 AI-only 기준선 측정 완료**, **4단계는 합의한 개선·전후 비교·요청 제한·통합 검증 완료**입니다.
[4단계 최종 검증 기록](support-program-request-limits.md#4단계-최종-통합-검증-2026-09-06)을 참고하세요.
**5단계는 기업마당 HTML 기반 최소 구현·검증 범위 완료**입니다. 추가 E12에서 64자리 인용 ID 복사 오류를
확인해 짧은 번호 선택·ID 복원 방식으로 수정했습니다. 수정 후 가상 4건과 공식 공고 2건의 질문 6개를 검증했고,
첫 공식 실행은 기대 상태 6건 일치·AI 의미 검토 5건 일치/1건 부분 일치였습니다. 당시 H01의 요약 누락과
이전 E01의 확정 불가한 실패 원인을 보존합니다. 전체 품질 합격·첨부/PDF 지원·운영 준비 완료는 아닙니다.
[5단계 검증 보고서](../evaluation/support-program-evidence/runs/official-flow-20260907-v1/README.md)와
[실행법](../evaluation/support-program-evidence/README.md)을 참고하세요.

5단계 후속 보완으로 H01의 대상 조건 요약 누락을 줄이기 위한 프롬프트 지침과 가상 질문 6개를 추가했습니다.
관련 범위·예외와 필수/우대/선택 관계를 보존하도록 했고, 공고별 하드코딩이나 검색 구조 변경은 없습니다.
**추가 20회로 가상 6건·공식 6건의 실측도 완료했습니다.** AI 의미 검토에서 모두 일치했고 공식 H01의
누락 보완과 기존 사례의 비회귀를 관찰했습니다. 단회 소규모 결과로 일반 정확도·통계적 개선을 주장하지
않습니다. [최신 검증 보고서](../evaluation/support-program-evidence/runs/official-flow-20260907-v2/README.md)에 전후 조건·사용량·한계를 보존했습니다.

**6단계는 API 없이 가능한 다중 제공처 준비를 구현했습니다.** 제공처별 준비 상태·부분 검색·복구 실패 격리,
K-Startup 공식 URL 표시와 RAG 미지원 사전 안내를 검증했습니다. 당시 실제 K-Startup Client·공고 수집·추가 데이터의
가치 표본 비교와 북마크는 미구현이었습니다(로그인은 이후 구현). 해당 준비의 유료 API 호출은 0회이며,
기존 5단계 보고서는 변경하지 않았습니다. [6단계 준비 범위·검증](support-program-multi-source-preparation.md)을 참고하세요.

**2026-09-09에는 K-Startup 실제 API Client·정규화·제공처별 동기화와 전용 필터를 추가했습니다.** 기존 벡터 색인을
공유하여 AI 추천과 직접 필터 검색에서 함께 사용할 수 있습니다. 기본 수집은 비활성이고, 최근 1년/모집 중 범위를
선택해 켭니다. 추가 데이터의 독립 품질·가치 비교와 K-Startup 공식 HTML 원문 질문은 별도 범위입니다.
현재 계약과 제약은 [K-Startup 수집](architecture.md#k-startup-수집-범위와-추가-분류)을 참고하세요.

후속 코드 검수에서는 학습용 예제를 보존하고 검색 입력·색인 장애·화면·평가 기록·Compose 정리 오류를
수정했습니다. 전체 테스트와 스텁 기반 Docker 통합 검증을 완료했으며, 유료 호출이나 새 제공처 구현은
추가하지 않았습니다. [검수·최적화 결과](code-audit-20260907.md)에 삭제 범위·검증 수치·한계를 기록했습니다.

## 사용자 기능

| 기능 | 상태 | 현재 동작 |
|---|---|---|
| 자연어 검색 | 구현됨 | 색인 준비가 확인된 제공처의 현재 공개 MySQL 공고에서 의미·키워드 결합 검색 후 AI 점수화, 0~5개 반환 |
| 검색 준비 상태 확인 | 구현됨 | 내부 상태 조회·응답 검증·검색 허용 판단 유지. 정상 상태의 패널·공고 수·인덱스·동기화 시각·제공처별 목록은 숨기고 준비 중/장애/부분 검색만 짧게 안내. `SEARCHABLE_WITH_PARTIAL_SOURCES`도 검색 허용 |
| 접수 상태 변경 | 구현됨 | 대화에서 접수 중/전체를 요청하고 제안 확인 후 `acceptingOnly`에 반영. 기본은 `true`, 전체는 예정·마감·상태 미확인도 포함. 별도 선택 상자 없음 |
| 익명 기업 조건 검색 | 구현됨 | 현재 소재지·업종·설립일·지원 목적을 대화로 전달·변경·해제하고 제안 확인 후 적용. POST body로 후보 검색과 AI 점수화에 반영. 수동 폼 없음 |
| 검색 당시 조건 표시 | 구현됨 | 각 검색의 조건을 메모리에 보관해 이후 변경된 조건과 구분. 해석 제안·미확정 초안은 사용자 확인 전까지 검색에 반영하지 않음 |
| 최신 목록 조회 | API 구현됨 | `query=`로 요청하면 AI 없이 최신 공고 최대 5개 반환; 채팅 UI는 빈 입력을 전송하지 않음 |
| 추천 결과 카드 | 구현됨 | 제목·기관·신청 기간·출처·관련도 점수와 대상·지역 자격 검토·본문 인용. 서버 관련도순 유지, 조건 확인/확인 필요 배지, 첨부 미검증 명시 |
| 공고 상세 화면 | 구현됨 | URL의 제공처 코드·원본 ID로 MySQL에서 재조회, 404·오류 안내, 원문 링크 제공 |
| 상세 직접 접속·새로고침 | 구현됨 | 검색 결과 상태가 없어도 같은 식별자로 API 조회 |

`GET /detail`은 동기화한 목록 데이터만 표시하고 외부 호출을 하지 않습니다. 반면
`POST /detail/answers`는 사용자가 질문한 기업마당 현재 공고에 한해 공식 상세 HTML을 추가 수집해 근거 답변을

허용 목록을 사용하며 기업마당과 K-Startup 공식 도메인 및 하위 도메인만 허용합니다. 위조 URL·알 수 없는
제공처가 섞이면 전체 응답을 거부합니다. K-Startup 수집·정규화·동기화는 구현했으며 데이터의 독립적인 추가 가치와
검색 품질 비교는 별도 검증이 필요합니다. K-Startup 원문 질문은 여전히 미지원입니다.

매 검색마다 Core는 현재 MySQL 공고·접수 상태를 읽고 AI는 Qdrant collection·전체 현재 버전·후보 조회를
검증합니다. 캐시는 모델·후보 수·배점·시간 상한을 바꾸지 않고 검증된 성공 값만 복사해서 재사용합니다.
TTL은 성공 후 재사용 기한이며 만료 즉시 물리 삭제를 보장하지 않습니다. 같은 입력의 동시 요청은 합류하고,
랭킹은 마지막 대기자의 취소 때 공유 작업을 종료합니다. 임베딩 수행 취소 시 남은 요청이 다시 실행하며
실패를 저장하거나 정상 결과로 보정하지 않습니다. 출력 축약은 미채택이며 기존 출력 계약을 유지합니다.
`OPENAI_RANKING_SERVICE_TIER` 미설정 시 코드·Compose 기본값은 `default`입니다. 제공 `.env.example`은
사용자 승인에 따라 `priority`(Fast)를 명시하며, 현재 Sol의 랭킹 토큰 단가는 일반 처리의 2배입니다.
대화 해석·RAG 답변·임베딩 설정은 바꾸지 않습니다. [검색 지연 개선 기록](search-latency-20260908.md)은
당시 일반 처리 배포·비교 결과로 보존합니다. 후속 지역 지침·schema는 회사·특정 사업장·개인 중 제한 주체를
먼저 구분하고 해당 주체의 주소가 미확인이면 UNKNOWN을 유지합니다. 같은 주체끼리 비교할 때는 서울·서초구의
하위 주소 미확인과 별도 허용 경로 없는 서울·안산의 지역 충돌을 구분합니다. 실제 허용된 이전·별도 사업장 대안은
각각 확인하고, 회사 주소만으로 다른 사업장의 부재나 개인 거주지를 확정하지 않습니다.
현재 Fast 설정·배포·추가 검증 상태는 [지역 충돌·Fast 기록](region-conflict-fast-20260908.md)을 참고하세요.

점수와 `MATCH` 판정은 모델의 판단이며 실제 신청 가능 여부나 선정 확률을 보장하지 않습니다.
코드는 응답 형식·숫자·제외 규칙을 검증하지만, 추천 이유가 원문에 의해 모두 뒷받침되는지까지
독립적으로 검증하지는 않습니다. 접수 상태 또한 파싱된 날짜와 알려진 문구 규칙을 따르며 신청 기간 밖의
모든 예외 조건을 반영하지 않습니다.

평가 도구는 후보 단계의 `macroRecallAtK`·무결과 오추천율과 최종 단계의 `macroRecallAt5`·`MRR@5`·무결과
오추천율을 분리해 계산합니다. `evaluation-fixture-export`는 현재 MySQL 카탈로그에서 미라벨 fixture 초안을
만들고, `evaluation-capture`는 실제 Search Service를 다시 구현하지 않고 같은 기준 날짜의 호출 흐름에서 나온
후보·최종 ID를 기록합니다. 실제 snapshot·capture는 `evaluation/support-program-search/runs/`에 보관합니다.
신규 fixture와 capture는 모두 색인 준비된 제공처만 조회합니다. 기존 고정 스냅샷·판정·캡처는 당시 조건의
원본으로 유지하며 이번 상태 필터로 과거 평가 결과를 다시 해석하지 않습니다.
현재 고정 스냅샷·AI 판정·모드 선택 결과는 Git 포함 대상이고 새 실행·임시 출력은 기본적으로 제외합니다.
[공유 자료 검증과 이어받기](../evaluation/support-program-search/runs/support-program-catalog-20260906-v1/README.md)를 따릅니다.
선택한 판정 출처와 실제 캡처 없이 검색 품질 점수를 주장하지 않으며, 의미 검색 결과
파일이나 캡처 파일을 제공하지 않으면 각각 출력의 `semantic`·`capture`는 `null`입니다.
[평가 자료와 실행법](../evaluation/support-program-search/README.md)을 참고하세요.

3단계 원표부터 지표까지 다시 확인할 수 있습니다. 4단계 전후 비교의 재계산 명령은 각 보고서에 있습니다.

현재 Health API는 서비스 응답과 Core→AI 연결을 확인합니다. 검색 화면의 `GET /api/v1/support-programs/readiness`는
마지막 전체 색인 준비 결과와 동기화 이력을 보여 주지만, MySQL·Qdrant·OpenAI의 실시간 Health를 한 번에
확인하는 endpoint는 아닙니다. CI 정의가 있다는 사실만으로 특정 원격 실행의 성공을 뜻하지는 않습니다.
실행 명령은 [서비스별 안내](../README.md#상세-문서)와 [CI 정의](../.github/workflows/ci.yml)에 있습니다.

## 현재 제약과 다음 작업

| 우선순위 | 작업 | 완료를 판단할 기준 |
|---|---|---|
| 1 | K-Startup 실데이터 반영·추가 가치 평가 | 수집 범위·임베딩 비용 확인 후 활성화하고, 제공처 간 중복·추가 공고·추천 품질을 독립 표본으로 비교. 연동 코드와 전용 필터 구현은 완료 |
| 2 | 외부 공개 전 운영 검증 | 배포 경계와 신뢰할 프록시·서버 수를 확정하고 실제 동시 부하·제한값·상시 지연/실패/사용량 관측을 검증. 현재 요청 제한과 평가 실행 로그를 운영 검증 완료로 취급하지 않음 |
| 3 | 추가 검색·답변 품질 개선 | 새로 관측되는 후보 누락·오추천·답변 누락·지연을 dev 근거와 같은 조건으로 전후 측정. H01 단회 개선을 일반화하지 않고 기존 자료·미확정 질문을 보존하며 이미 노출된 heldout에 맞춰 튜닝하지 않음 |
| 4 | 사용자 기능 확장 | 로그인·세션 위에 회원가입·이메일 인증·기업 등록·영구 기업 프로필·북마크의 제품 범위를 정한 뒤 API·저장·화면까지 연결. C01의 익명 조건 입력과는 별도 범위 |

검색은 현재 MySQL에서 색인 준비된 제공처의 공개 공고만 읽습니다. 비어 있지 않은 검색어를 처리할 때는 접수 상태
필터를 통과한 공고의 제공처 포함 ID와 문서 해시를 내부 API에 보냅니다.
검색·색인 경계의 공고 수 제한은 20,000개이며, 그 이상의 카탈로그나 동시 사용자 부하는 검증된 범위가 아닙니다.
오래된 벡터의 저장 공간 정리도 아직 자동화하지 않았습니다. 규모 확장 전에 조회 비용과 색인 수명주기를
측정·개선해야 합니다.

현재 Compose는 개발 환경이며 이메일 인증, 운영 접근 제어, 배포 자동화, 백업·복구 절차는 별도 구현·검증이
필요합니다. 로그인·세션은 동작하지만 Compose는 개발용 시드 로그인을 켜고 쿠키 `Secure`를 끈 상태입니다. 문서 기반 RAG는 기업마당 공식 HTML 한 종류의 공고별 명시적 질문에만 구현되어 있으며,
대화 이력 저장이나 첨부파일 기반 RAG가 구현된 것은 아닙니다.
