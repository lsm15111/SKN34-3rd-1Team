# 도움말 챗봇 화면 구현 계획과 결과

기준일 2026-09-12. 주제 적합성 판단, 구현 순서, 그리고 실제로 만든 범위를 정리한 문서입니다.
C0·C1·C2·C2.5는 구현·검증을 마쳤고 C3·C4는 남아 있습니다. 8장에 구현 결과가 있습니다.
확정 화면 명세는 [도움말 챗봇 화면 명세](https://claude.ai/code/artifact/fa8aceb4-041e-4911-890f-72146bfeb030)이며
치수·문구는 그 명세를 따르고 이 문서에서 새로 짓지 않습니다.

## 1. 주제 적합성 — 적합

주제는 `LLM을 활용한 내·외부 문서 기반 응답 시스템`입니다. 두 축을 나눠 보면 현재 상태는 이렇습니다.

| 축 | 문서 | 현재 구현 | 근거 위치 |
|---|---|---|---|
| 외부 문서 | 기업마당·K-Startup 공고 상세 원문 | 구현됨 — 청크 색인, 질문당 근거 검색, 인용, 근거 없으면 기권 | `backend/ai-service/app/support_program_evidence` |
| 외부 문서 | 공식 첨부 PDF·HWPX | 구현됨 — 안전 추출 후 신청 문항 구조화, `evidenceBlockId`·`evidenceQuote` 검증 | `backend/ai-service/app/application_preparation` |
| 내부 문서 | 제품 사용법·정책·용어 | **없음** | — |

도움말 챗봇은 비어 있는 세 번째 칸을 정확히 채웁니다. 주제에 맞습니다.

다만 두 가지를 짚어야 합니다.

**첫째, 도움말 챗봇 단독으로는 주제의 절반입니다.** 명세의 기권 1번은 "공고 내용은 도움말에서
답하지 않습니다"이고, 이 문장은 외부 문서 축을 의도적으로 잘라 냅니다. 제품 판단으로는 옳지만
주제 관점에서는 한 창에서 내부·외부를 모두 근거로 답하는 그림이 사라집니다.
해법은 작습니다 — **기권을 위임으로 바꿉니다.** 공고 상세·원문 질문 화면에서 패널을 열었다면
"이 공고에 질문하기"가 화면을 옮기는 대신 같은 패널 안에서 기존 근거 답변 API를 호출하고,
답변 카드에 `내부 문서`·`공고 원문` 출처 배지를 붙입니다. C2 뒤 한 단계(C2.5)면 됩니다.

**둘째, RAG를 쓰지 않는 결정은 항목 10~50개일 때만 성립합니다.** 지금 콘텐츠가 10항목이라
전량 주입이 맞고, 검색 실패가 0이라는 이점도 실제입니다. 내부 문서 범위를 `docs/*.md`까지
넓히는 순간 전제가 깨지므로, 그때 색인을 붙입니다. 지금 미리 만들지 않습니다.

주제 심사에서 내세울 지점은 "벡터 검색을 썼다"가 아니라 **근거 없으면 답하지 않는다**입니다.
`INSUFFICIENT_EVIDENCE` 기권, 인용 칩, 갱신일 표시, `quote`가 원문의 부분 문자열인지 재검증하는
Core 계약이 이미 있고, 도움말 챗봇도 같은 규칙을 그대로 따릅니다.

## 2. 선행 조건 — 데이터 계층을 다시 만들었습니다

인수인계 문서가 완료로 적은 5개 파일은 이 저장소의 어떤 브랜치에도 없었습니다
(`git log --all -- "*help*"`로 확인). 다른 기기의 커밋되지 않은 로컬 파일입니다.

원래 기기에서 가져올 수 없어 화면 명세에 드러난 필드를 근거로 타입과 콘텐츠를 다시 만들었습니다.
따라서 필드 이름이 원본과 다를 수 있습니다. 나중에 원본이 나타나면 **둘을 합치지 말고 한쪽을 버려야**
합니다. 두 벌이 남으면 도움말이 서로 어긋납니다.

## 3. 단계

| 단계 | 범위 | AI 호출 | 상태 |
|---|---|---|---|
| C0 | 타입·콘텐츠 10항목·불변식 테스트 | 0 | 완료 |
| C1 | 런처 · 패널 · 첫 화면 · 추천 질문 · 항목 답변 · 이어서 물어보기 | 0 | 완료 |
| C2 | 자유 질문, 기권 3종, 인용 재검증, 중지 | 질문당 1 | 완료(스트리밍 제외) |
| C2.5 | 공고 질문을 같은 패널에서 원문 근거 답변에 위임 + 출처 배지 | 위임 시 1 | 완료 |
| C3 | 복사 · 단축키 · 세션 기억 | — | 남음 |
| C4 | 피드백 분류 저장, 기권 질문 수집 | — | 남음 |

C1이 화면단의 전부입니다. 추천 질문을 누르면 그 항목의 `summary`와 `body`를 그대로 그리므로
네트워크 0회로 아홉 상태 중 ①②⑤⑥⑨가 완성됩니다. ③④⑦은 C2에서 붙습니다.

### C1 작업 순서

1. `HelpLauncher` — 52px, 우 24 / 하 24, `/app/chat`과 `/`에서는 하 92. 열리면 ✕로 토글.
2. `HelpPanel` — 352 × ≤560, 모바일 전체 화면 시트. 열면 입력에 포커스, Tab 순환, Esc로 닫고
   런처로 복귀. `WorkspaceModal`의 포커스 처리를 그대로 따릅니다.
3. `HelpSuggestionList` — `helpEntriesForRoute(pathname)` 3개(모바일 2개). 없으면 전역 항목.
4. `HelpAnswerCard` — 결론 → 근거 → 행동 → 도구줄. 순서를 바꾸지 않습니다.
5. `HelpCitationChip` — 클릭 시 요약 팝오버와 `updatedOn`. `shared/workspace/HelpTip.tsx`의
   말풍선 구조를 참고하되 클릭 방식이라 별도 컴포넌트로 둡니다.
6. `related`로 "이어서 물어보기" 한 개.

### C2에서 붙는 것

- `POST /api/v1/help/answers` — Core가 프롬프트와 항목 전량을 AI Service에 넘기고 스트리밍으로
  받습니다. 흐름은 `HTTP API → Service → Agent → OpenAI → Response`입니다.
- 인용 재검증 — 답변이 지목한 항목 id가 실제 목록 안에 있는지 Core가 확인하고 어긋나면 502.
  공고 근거 답변이 `quote` 부분 문자열을 검증하는 것과 같은 규칙입니다.
- 기권 3종(공고 내용 / 제도 상식 / 안내에 없음)과 오류 카드. 실패를 정상 답변으로 숨기지 않습니다.

않는 상태를 Redux에 올리지 않습니다.

## 5. 붙일 자리

`App.tsx`가 `<Routes>`를 그대로 반환하므로 조각으로 감싸 라우트 밖에 런처를 한 번만 둡니다.
로그인·회원가입·비밀번호 재설정처럼 껍데기를 쓰지 않는 단독 화면과 `/report-email`에서는 숨깁니다.
공개 화면에는 노출합니다 — 처음 온 사람이 가장 많이 막히기 때문입니다.

## 6. 기능 — 넣은 것과 뺀 것

### 넣었습니다

| 기능 | 이유 |
|---|---|
| 화면별 추천 질문 3개(모바일 2개) | 빈 입력창은 무엇을 물어야 할지 모르게 합니다. 네트워크 0회 |
| 항목 인용 칩 + 갱신일 | 근거 표시가 이 시스템의 핵심입니다. 오래된 안내를 감추지 않습니다 |
| 근거 없으면 기권 | 틀린 답 하나가 기권 열 번보다 나쁩니다 |
| `status`·`limitation` 노출 | 준비 중 기능을 되는 것처럼 안내하는 것이 가장 큰 사고입니다 |
| AI가 만든 답에만 `◈ AI 생성` | 항목을 그대로 보여 준 답변에 붙이면 사실과 다릅니다 |
| 모든 항목 답변이 갈 곳으로 끝남 | `category: 'blocker'`는 `action` 필수를 테스트가 강제합니다 |
| 공고 질문을 같은 패널에서 위임 | 내·외부 통합. 주제와 1:1로 맞는 지점 |
| 중지 버튼 | 입력줄에 고정합니다. 말풍선 옆이면 답변에 밀립니다 |
| Core·화면 양쪽의 인용 재검증 | 요청 밖 항목을 가리키는 답변은 그리지 않습니다 |

## 7. 정한 결정

| # | 결정 | 정한 값 |
|---|---|---|
| 1 | 데이터 계층 | 가져오기 불가라 다시 씀. 원본이 나타나면 한쪽을 버립니다 |
| 2 | 패널 본문 크기 | 명세대로 13px + 행간 1.72(제품 일관성). KRDS 16px 권고와 상충하는 것은 그대로 남습니다 |
| 3 | `/help` 매뉴얼 경로 | 이번 범위 밖. 그래서 답변 카드에 "매뉴얼에서 자세히"를 넣지 않았습니다 |
| 4 | 공고 질문 위임 | 채택. 화면을 옮기지 않고 같은 패널에서 답합니다 |
| 5 | 도움말 항목의 소유자 | 화면이 소유하고 요청마다 보냅니다. Core는 사본을 두지 않습니다 |

5번은 트레이드오프가 있습니다. 항목이 요청 본문으로 오가므로 요청이 커지고, 클라이언트가 항목을
바꿔 보낼 수 있습니다. 그 답은 그 사용자에게만 보이고 저장되지 않아 영향 범위가 그 세션 안에 있으며,
Core는 길이·개수·형식을 검사하고 인용이 그 요청의 항목 안인지 확인합니다. 매뉴얼 화면이 생겨
서버가 항목을 갖게 되면 그때 소유자를 Core로 옮기는 편이 낫습니다.

## 8. 구현 결과

### 흐름

```text
추천 질문 · 같은 뜻의 질문        → 화면이 가진 항목을 그대로 표시 (AI 0회, 네트워크 0회)
그 밖의 자유 질문                → POST /api/v1/help/answers
                                   → HelpAnswerController → 요청량 한도
                                   → HelpAnswerService → AiHelpAnswerClient
                                   → AI Service /internal/v1/help/answers
                                   → Agent → OpenAI → 인용 번호를 항목 ID로 복원
                                   → Service가 기권 문장 제거 → Core가 인용 재검증
공고 내용 질문(공고 화면)         → 같은 패널에서 기존 공고 원문 근거 답변으로 위임
```

### 명세 아홉 상태

①런처 ②첫 화면 ③준비 중 ⑤답변 완료 ⑥인용 팝오버 ⑦기권 ⑧스크롤 중 ⑨모바일을 구현했습니다.
**④ 토큰 스트리밍은 넣지 않았습니다.** Core와 AI Service 두 계층에 SSE를 새로 놓아야 하고,
리서치대로 SSE는 취소 신호를 서버로 보내지 못해 중지해도 과금이 계속됩니다. 대신 첫 글자 전까지
스켈레톤(③)을 보여 주고 중지 버튼으로 화면의 요청만 끊습니다. 스트리밍은 별도 단계로 남깁니다.

### 명세와 다르게 한 것

| 명세 | 실제 | 이유 |
|---|---|---|
| 답변에 항상 `◈ AI 생성` | AI가 만든 답변에만 | 항목을 그대로 보여 준 답변은 AI 생성물이 아닙니다 |
| 하단 "도움말 범위 안에서만 답합니다 · AI 생성" | 앞부분만 | 같은 이유. AI 답변에는 카드 안에 표시가 붙습니다 |
| 런처와 패널에 각각 ✕ | 패널의 ✕만 보조기술에 노출 | 명세의 "닫기 버튼을 두 곳에 두지 않는다"를 따랐습니다. 런처는 마우스 토글로 남습니다 |
| 답변 카드에 "매뉴얼에서 자세히" | 없음 | `/help` 매뉴얼 화면이 아직 없어 죽은 링크가 됩니다 |
| "오늘 N회 남음" 한도 표시 | 없음 | 서버가 남은 횟수를 알려 주지 않습니다. 한도 초과는 오류 카드로 알립니다 |
| 기권 · 없음의 "질문을 기록해 두었습니다" | 문장 삭제 | 기록하지 않습니다. 사실이 아닌 문장을 쓰지 않습니다 |

### 콘텐츠 정정

인수인계 문서의 "검색 10초 제한"은 코드와 맞지 않았습니다. 실제 화면 제한은 조건 해석 40초,
검색 90초입니다(`useSupportProgramChat.ts`). 10초는 검색 준비 상태 조회의 제한입니다.
도움말 항목에는 코드에서 확인한 값을 적었습니다.

| Core API | `./gradlew test --tests "ai.govbiz.core.help.*"` | 13건 통과 |
| 실제 화면 | Compose 개발 스택에서 데스크톱·모바일 폭 | 런처·패널·추천 질문·항목 답변 확인 |

`main`의 프런트엔드 기준선은 실패 0건이었습니다(작업 전 968건 전부 통과). 인수인계 문서의
"기존 실패 39건"은 이 저장소 상태와 맞지 않습니다.

Core API 전체 `./gradlew test`는 이 개발 PC에서 Testcontainers MySQL 연결 실패
(`Communications link failure`)로 Spring context 테스트가 무더기로 실패합니다. 작업 전 커밋
`cf2a280`을 별도 worktree에 꺼내 같은 명령을 돌려 비교했습니다.

| 실행 | 테스트 | 실패 |
|---|---:|---:|
| 작업 전 `cf2a280` | 1,167 | 176 |
| 이번 변경 | 1,180 | 176 |

실패 수가 같고 늘어난 13건은 새로 추가한 도움말 테스트이며 모두 통과했습니다. 이 변경과 무관한
환경 문제이지만, **DB가 뜨는 환경에서 전체 테스트를 다시 돌려야 합니다.**

## 11. 준비 중 표기 제거와 자주 묻는 질문 화면 (2026-09-12 추가)

사용자 요청으로 "준비 중"이라는 안내를 화면에서 모두 뺐습니다.

- 도움말 항목 계약에서 `status` 필드와 `feature-status` 분류를 없앴습니다. 프런트·Core·AI Service 세 곳의
  계약과 프롬프트 규칙에서 함께 지웠습니다. 지금 안 되는 것은 `limitation` 한 줄로 계속 알립니다.
- `feature-status-preparing` 항목을 지우고 그 자리에 `saved-program-basics`(관심 공고함)를 넣었습니다.
  관심 공고함이 실제로 출시되어 준비 중 항목이 설명하던 예시가 사라졌기 때문입니다.
- 파트너 모집 상세의 비활성 버튼 다섯 개(모집글 저장·기업 프로필 보기·관심 공고에 추가·숨기기·신고)를
  자리째 없앴습니다. 눌리지 않는 버튼은 자리를 지키는 값보다 "미완성"으로 읽히는 비용이 큽니다.
- 신청 준비의 `문서 지원 준비 중`은 `문서 지원 없음`으로 고쳤습니다. 이건 예정이 아니라 그 제공처를
  지원하지 않는다는 사실이라 정보를 지우지 않고 표현만 바꿨습니다.

이어서 도움말 항목 한 벌을 두 번째 표면에 붙였습니다. `/faq`와 `/app/faq`는 `helpContent.ts`를 그대로 읽어
분류(막히기 쉬운 곳 / 화면에 보이는 말의 뜻)·검색·아코디언으로 보여 주고, 답마다 갈 곳과 갱신일을 답니다.
검색은 화면 안에서만 걸러 네트워크를 쓰지 않고, 검색 엔진과 AI 도우미가 인용하도록 FAQ 구조화 데이터를 함께 싣습니다.
챗봇과 FAQ가 같은 원본을 읽으므로 두 곳의 안내가 어긋날 수 없습니다.
